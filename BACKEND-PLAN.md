# BACKEND-PLAN.md — заявки, админка, контент и предоплата

План бэкенда для сайта https://stvnislv.netlify.app/ и Telegram Mini App. По нему бэкенд разрабатывается целиком, этап за этапом.

Решения владельца от 11.11.2026:
- **Заявки и контент** владелец ведёт в админке внутри Mini App. Админка видна только ему, вход через его Telegram-аккаунт.
- **Хранение — Supabase** (решение от 11.11.2026, как в уроке): одна таблица `kv`, доступ только с сервера. **Сервер — Netlify Functions**, VPS пока не арендуется. Риск по закону о персональных данных понятен (см. раздел 8).
- **Ответ клиенту** идёт через бота: владелец пишет, бот пересылает клиенту, ответы клиента приходят владельцу.
- **Предоплата:** сумма задаётся в конкретной заявке, клиент получает ссылку на оплату ЮKassa. Пока только тестовый магазин.
- **Возможно, позже проект переедет на российский VPS.** Для этого в коде остаются драйвер `file` и сервер `server/server.mjs`, см. раздел 2.1.
- Telegram ID владельца — `288440954` (`OWNER_TELEGRAM_ID`).

Если план расходится с `brief.md`, сначала обновить бриф: он главный документ.

## 1. Что получится

1. Клиент на сайте или в Mini App смотрит услуги и работы и оставляет заявку: что нужно, бюджет, сроки, контакт.
2. Заявка за секунды приходит владельцу в чат с ботом @stvnislv_bot, с кнопками статуса.
3. В Mini App владелец видит вкладку «Заявки» со всеми заявками: меняет статус («Новая» → «В работе» → «Готово»), пишет клиенту, выставляет предоплату, удаляет.
4. Во вкладке «Контент» владелец меняет услуги, цены, плашку скидки и портфолио с картинками. Сайт и Mini App сразу показывают новое, код править не нужно.
5. Клиент получает ссылку на предоплату, платит в ЮKassa, заявка помечается «Оплачено» после проверки платежа через API ЮKassa.

### Чего в плане нет (и почему)

| Нет | Почему |
|---|---|
| Личный кабинет клиента | Клиенту хватает бота: он получает ответы и ссылку на оплату |
| Несколько администраторов, роли | Владелец один. Его Telegram ID задаётся в настройках |
| Отдельные таблицы под заявки, услуги, портфолио | Одна таблица `kv` в Supabase: так же устроен драйвер `file`, поэтому переезд — это копирование данных. Заявки владелец смотрит в админке Mini App |
| Рассылки, CRM-воронка, аналитика | Не просили |
| Реальные платежи | Сначала нужна фискализация (чеки) в кабинете ЮKassa, см. этап 7 |
| Редактирование остальных текстов сайта («Обо мне», шаги, первый экран) | Владелец просил только услуги и портфолио. Эти тексты остаются в коде |

## 2. Архитектура

```
 Сайт (index.html) ─┐                                        ┌─ Supabase: таблица kv (заявки, контент, служебное)
                    ├─ fetch /api/* ─▶ Netlify Functions ────┤   картинки — Supabase Storage (этап 5)
 Mini App (tg-app) ─┘   (stvnislv.netlify.app)               ├─ Telegram Bot API (уведомления, ответы)
                                                             └─ ЮKassa API (платежи, сверка) — отложено
 Telegram ── webhook ──▶ /api/telegram
 ЮKassa   ── webhook ──▶ /.netlify/functions/yookassa-webhook
```

- **Функции — Netlify** основного сайта `stvnislv.netlify.app` (Node 22). Каждая функция в `netlify/functions/` — тонкая обёртка: логика лежит в `server/handlers/` и `server/lib/`. Маршруты `/api/...` задаются через `export const config = { path: … }`, правки `netlify.toml` не нужны.
- **Данные — Supabase**, таблица `public.kv` (`supabase/schema.sql`): раздел, ключ, JSON, etag. RLS включён без политик, права `anon` и `authenticated` отозваны: таблицу видит только сервер с секретным ключом (`SUPABASE_SECRET_KEY`). Браузер к Supabase напрямую не обращается, публичный ключ не используется. Регион проекта — East US (Ohio), рядом с функциями Netlify.
- **Без библиотек:** драйвер Supabase ходит в REST API (PostgREST) обычным `fetch`, `@supabase/supabase-js` не нужен. Условная запись по etag: `PATCH … ?etag=eq.<старый>` (обновит, только если никто не успел раньше), «только новая» — `POST` с `resolution=ignore-duplicates`.
- **Бот переходит с long polling на webhook** (`/api/telegram`), поэтому работает круглосуточно. Сервера Netlify находятся за рубежом, так что VPN для `api.telegram.org` не нужен. `bot/bot.mjs` после переезда удаляется: при включённом webhook он всё равно не запустится.
- **Mini App опубликован в двух местах:** `stvnislv-app.netlify.app` и `stvnislv.netlify.app/tg-app/`. API разрешает запросы с обоих адресов (список в `ALLOWED_ORIGINS`). Авторизация идёт заголовком, а не cookie, поэтому CORS простой.
- **Офлайн-режим сохраняется.** `index.html` по-прежнему открывается двойным щелчком: если `/api/content` недоступен, сайт показывает данные, встроенные в файл. Mini App так же использует `data.js`. Заявку и оплату без сервера отправить нельзя, и форма прямо об этом говорит.
- **Бесплатный тариф Supabase:** проект ставится на паузу после недели без запросов — ежедневная функция `purge.mjs` (этап 7) держит его активным; автоматических резервных копий нет — их делает `scripts/storage-copy.mjs` (выгрузка всех данных).

### 2.1. Возможный переезд в Россию — как он заложен в код

- **Хранилище за одним интерфейсом** (`server/lib/store.mjs`): `get` / `set` (с условиями `onlyIfMatch` по etag и `onlyIfNew`) / `delete` / `list(prefix)`. Драйвер выбирается переменной `STORAGE_DRIVER`:
  - `supabase` — основной, по умолчанию;
  - `file` — JSON-файлы в папке `STORAGE_DIR`, для российского VPS: атомарная запись через временный файл и `rename`, проверка etag под замком на ключ. Рассчитан на один процесс Node;
  - `blobs` — Netlify Blobs, запасной;
  - `memory` — для тестов.
  Один и тот же набор тестов гоняется на всех драйверах, поэтому поведение при переезде не меняется.
- **Обработчики пишутся на стандартных `Request` → `Response`**, без объекта `context` Netlify в логике (IP клиента передаёт обёртка). Для VPS уже есть сервер `server/server.mjs` на `node:http` (маршруты — объект `routes`); перед ним встанет Caddy (https), а расписание заменит `systemd`-таймер.
- **Данные переносятся скриптом** `scripts/storage-copy.mjs` (этап 7): копирует все разделы из одного драйвера в другой (Supabase → файлы) через тот же интерфейс.
- **Переезд — это:** аренда VPS, `STORAGE_DRIVER=file`, копирование данных скриптом, перенос webhook бота и ЮKassa на новый адрес. Код заявок, бота и админки не меняется.

## 3. Какие данные хранить

Хранилище — таблица `kv` в Supabase (через `store.mjs`). В каждой записи есть `version`. Когда две записи могут прийти одновременно (уведомление ЮKassa и действие владельца), запись делается условно (`onlyIfMatch` по etag) и при конфликте повторяется.

### 3.1. Заявка — store `leads`, ключ `<leadId>` (UUID)

| Поле | Тип | Откуда |
|---|---|---|
| `id` | UUID | сервер |
| `number` | целое, 1, 2, 3… | сервер, счётчик `meta/lead-counter`. Нужен для подписи «Заявка №12» |
| `source` | `"site"` \| `"miniapp"` | сервер: по наличию проверенного initData |
| `createdAt`, `updatedAt` | ISO-время | сервер |
| `status` | `"new"` \| `"in_progress"` \| `"done"` | сервер; меняет только владелец |
| `serviceId` | id услуги или `"other"` | клиент, выбор из списка |
| `task` | строка 1–2000 | клиент: «Что нужно сделать» |
| `budget` | `"lt30"` \| `"30_60"` \| `"60_100"` \| `"gt100"` \| `"unknown"` | клиент; подписи «до 30 000 ₽» и т. д. — в `content.mjs` |
| `deadline` | `"asap"` \| `"2w"` \| `"month"` \| `"flexible"` | клиент: «срочно», «2 недели», «месяц», «не важно» |
| `contact.name` | строка 1–100 | клиент |
| `contact.method` | `"telegram"` \| `"email"` \| `"phone"` | клиент; в Mini App по умолчанию `telegram` |
| `contact.value` | строка до 254, проверка по `method` | клиент; в Mini App подставляется `@username` |
| `tg` | `{ userId, chatId, username, firstName }` \| `null` | сервер: из initData (Mini App) или после перехода клиента в бота по ссылке (сайт) |
| `canMessage` | boolean | сервер: бот может писать клиенту (клиент разрешил доступ в Mini App или сам нажал «Старт» у бота) |
| `linkToken` | 22 символа base64url | сервер: для ссылки `t.me/stvnislv_bot?start=l_<token>` |
| `consent` | `{ at, policyVersion }` | сервер, при обязательной галочке согласия |
| `ownerMessageId` | число | id уведомления в чате владельца, чтобы обновлять в нём статус |
| `note` | строка до 2000 | владелец, видит только он |
| `messages` | до 200 записей `{ from: "owner"\|"client", text, at }` | переписка через бота |
| `payment` | объект или `null`, см. 3.2 | владелец + сервер |
| `doneAt` | ISO-время \| `null` | сервер, от него считается срок хранения |

**Индекс** `leads/_index` — краткие строки для списка `{ id, number, status, createdAt, name, serviceId, paymentStatus, unread }`. Он обновляется вместе с заявкой, поэтому список открывается одним чтением, а не сотней.

**Связи с Telegram** (store `leads`):
- `tg-msg/<messageId>` → `leadId`: на какое сообщение владелец ответил;
- `tg-chat/<chatId>` → `leadId` последней открытой заявки клиента: куда положить сообщение клиента.

### 3.2. Предоплата — поле `payment` в заявке

| Поле | Тип |
|---|---|
| `amountKopeks` | строка, целое число от 100 до 100 000 000 (от 1 ₽ до 1 000 000 ₽) |
| `description` | строка 1–128 (ограничение ЮKassa), например «Предоплата 50%: лендинг» |
| `token` | 32 символа base64url — секрет ссылки `/api/pay/<token>` |
| `status` | `"awaiting"` (ссылка выдана) \| `"pending"` (клиент открыл оплату) \| `"succeeded"` \| `"canceled"` |
| `paymentId` | id платежа ЮKassa \| `null` |
| `createdAt`, `paidAt` | ISO-время |

Ссылка-токен `pay/<token>` → `leadId` хранится отдельно, чтобы найти заявку по ссылке. Платёж в ЮKassa создаётся, только когда клиент открывает ссылку, а не заранее: так ссылка не устаревает.

### 3.3. Контент — store `content`

`content/services`:
```json
{ "version": 3, "discount": "Скидка 5%", "note": "Точную цену назову, когда узнаю задачу.",
  "items": [ { "id": "sites", "title": "Сайты и лендинги", "description": "…", "priceFrom": 25000,
               "term": "от 5 дней", "message": "Здравствуйте! Хочу обсудить сайт или лендинг.", "visible": true } ] }
```
- `id`: латиница, 2–32 символа, после создания не меняется (на него ссылаются заявки);
- `title` до 60 символов, `description` до 300;
- `priceFrom`: целые рубли или `null` (на сайте «от … ₽»);
- `term` до 30 символов, `message` до 200;
- порядок карточек совпадает с порядком в массиве.

`content/portfolio`:
```json
{ "version": 5, "items": [ { "id": "site", "title": "Мой сайт", "description": "…", "tags": ["Лендинг", "2026"],
  "image": "media/abc.webp", "preview": "site", "url": "https://stvnislv.netlify.app/", "visible": true } ] }
```
- `image` — ключ картинки в `media` или `null`;
- `preview` — `"site"` \| `"app"` \| `null`: нарисованная миниатюра, если картинки нет;
- `url` — только `https://` или `null`;
- `tags` — до 4 штук, до 24 символов каждый.

Если записей ещё нет, `content.mjs` отдаёт значения по умолчанию: те, что сейчас в `index.html` (`site`) и `tg-app/data.js`.

### 3.4. Картинки — Supabase Storage, бакет `media` (закрытый)

Картинки — не JSON, поэтому лежат не в `kv`, а в Supabase Storage; в интерфейс хранилища добавятся `getBytes` / `setBytes` (для драйвера `file` — файлы в папке). Ключ — `<uuid>.webp|jpg|png`, тип файла хранится вместе с ним. До 2 МБ. Админка перед загрузкой сама сжимает картинку до 1600 px по длинной стороне. Отдаются через `GET /media/:key` с `Cache-Control: public, max-age=31536000, immutable`: ключ уникален, поэтому кэш никогда не устаревает.

### 3.5. Служебное — store `meta`

- `lead-counter` — номер для следующей заявки;
- `rate/<sha256(ip+соль)>/<час>` — сколько заявок было с адреса за этот час. Сам IP не хранится. Старые записи удаляет `purge.mjs`.

## 4. API

Общие правила для всех ответов:
- JSON и `Cache-Control: no-store`; исключения — `/api/content` и `/media`;
- ошибки в виде `{ "error": "<текст по-русски для человека>" }`;
- тело запроса — JSON до 8 КБ (картинки — до 2 МБ); лишние поля дают 400;
- CORS разрешён только для адресов из `ALLOWED_ORIGINS`.

### 4.1. Публичные

| Метод и путь | Кто вызывает | Что делает | Ответ |
|---|---|---|---|
| `GET /api/content` | сайт, Mini App | Видимые услуги, плашка, портфолио. Поля `visible` и служебные не отдаются | 200; кэш `public, max-age=60` и CDN-кэш на 60 с: правка владельца видна в течение минуты |
| `POST /api/leads` | сайт, Mini App | Создать заявку (см. 5.1) | 201 `{ number, telegramLink }`; 400 — ошибка поля; 403 — чужой Origin или неверный initData; 429 — слишком много заявок |
| `GET /api/pay/:token` | клиент по ссылке | Создаёт платёж ЮKassa (или берёт уже созданный и ещё не оплаченный) и перенаправляет на страницу оплаты | 302 на ЮKassa; 404 — ссылки нет; 410 — уже оплачено или отменено владельцем |
| `GET /api/pay/:token/status` | сайт после возврата из ЮKassa | Статус оплаты | 200 `{ status, amount, description }` |
| `POST /api/telegram` | Telegram | Обновления бота (см. 5.3) | 200 всегда; без верного `X-Telegram-Bot-Api-Secret-Token` — 401 |
| `POST /.netlify/functions/yookassa-webhook` | ЮKassa | Как сейчас: сверка через API ЮKassa, затем статус платежа в заявке и уведомление владельцу | 200; 503 — ЮKassa повторит |
| `GET /media/:key` | все | Картинка портфолио | 200 / 404 |

### 4.2. Админка — только владелец

Каждый запрос несёт заголовок `Authorization: tma <initData>` (строка `Telegram.WebApp.initData`). Сервер проверяет:
1. подпись HMAC-SHA256 по алгоритму Telegram (ключ = HMAC("WebAppData", токен бота));
2. `auth_date` не старше 24 часов;
3. `user.id` равен `OWNER_TELEGRAM_ID`.

Иначе — 401 или 403. Вне Telegram админка недоступна: это сделано намеренно.

| Метод и путь | Что делает |
|---|---|
| `GET /api/admin/me` | 200, если вы владелец. По нему Mini App решает, показывать ли вкладки админки (защиту обеспечивают остальные проверки, а не скрытие вкладок) |
| `GET /api/admin/leads?status=new` | Список из индекса, новые сверху |
| `GET /api/admin/leads/:id` | Заявка целиком, с перепиской и оплатой. Снимает отметку «непрочитано» |
| `PATCH /api/admin/leads/:id` | `{ status?, note? }`. Смена статуса обновляет и уведомление в чате владельца |
| `POST /api/admin/leads/:id/messages` | `{ text }` до 4000 символов. Бот отправляет его клиенту. 409, если `canMessage = false`: тогда админка показывает контакт клиента и кнопку «Скопировать» |
| `POST /api/admin/leads/:id/payment` | `{ amountKopeks, description, send: true\|false }`. Создаёт или заменяет неоплаченную ссылку. При `send` бот отправляет клиенту кнопку «Оплатить». Ответ — ссылка `https://stvnislv.netlify.app/api/pay/<token>`. 409, если уже оплачено |
| `DELETE /api/admin/leads/:id/payment` | Отменить неоплаченную ссылку |
| `DELETE /api/admin/leads/:id` | Удалить заявку со всеми связями: по просьбе клиента или если это спам |
| `GET /api/admin/content` | Услуги и портфолио целиком, включая скрытые, с `version` |
| `PUT /api/admin/content/services` | Заменить документ целиком. Заголовок `If-Match: <version>`; 409, если документ уже изменён в другом окне |
| `PUT /api/admin/content/portfolio` | То же для портфолио |
| `POST /api/admin/media` | Тело — файл (`image/webp`, `image/jpeg`, `image/png`, до 2 МБ, тип проверяется по первым байтам файла). Ответ `{ key, url }` |
| `DELETE /api/admin/media/:key` | Удалить картинку. 409, если она ещё используется в портфолио |

## 5. Как это работает

### 5.1. Заявка

1. **Форма.** На сайте форма заявки в разделе «Контакты» заменяет нынешнюю выключенную форму и тестовую форму оплаты. В Mini App она появляется на экране «Связаться» и открывается кнопками «Обсудить» с уже выбранной услугой. Поля: услуга, что нужно сделать, бюджет, сроки, имя, способ связи и контакт. Обязательная галочка «Согласен на обработку персональных данных» со ссылкой на политику. Скрытое поле-ловушка для ботов.
2. **В Mini App** перед отправкой вызывается `Telegram.WebApp.requestWriteAccess()`. Если клиент разрешил, `canMessage = true`. Имя и `@username` подставляются из Telegram, их можно поправить.
3. **Сервер:** проверяет Origin или initData, поля, ловушку и лимит (5 заявок в час с одного адреса) → выдаёт номер → сохраняет заявку и индекс → шлёт уведомление владельцу.
4. **Уведомление владельцу** (HTML с экранированием всех полей):
   ```
   🆕 Заявка №12 · сайт
   Услуга: Сайты и лендинги · Бюджет: 30–60 тыс. ₽ · Срок: 2 недели
   Задача: …
   Анна · telegram: @anna
   [В работе] [Готово] [Открыть в админке]
   ```
   Если Telegram не ответил, заявка всё равно сохранена, а уведомление повторит `purge.mjs` (флаг `notified: false`). Клиент заявку не теряет.
5. **Клиенту** показывается ответ «Заявка №12 принята. Отвечу в течение дня.» Клиенту с сайта также предлагается кнопка «Получать ответ в Telegram»: ссылка `t.me/stvnislv_bot?start=l_<linkToken>`. Если клиент её нажмёт, бот привяжет его чат к заявке и сможет пересылать ему ответы.

### 5.2. Статусы

`new` → `in_progress` → `done`. Владелец может вернуть любой статус назад. Статус меняется только владельцем: в админке или кнопкой под уведомлением. При `done` ставится `doneAt`. Статус оплаты хранится отдельно и статус заявки не меняет.

### 5.3. Бот (`/api/telegram`)

| Входящее | Действие |
|---|---|
| `/start`, `/help`, `/contact` | Те же ответы, что в нынешнем `bot/bot.mjs`, кнопка открывает Mini App |
| `/start l_<token>` | Привязать чат к заявке с этим `linkToken`, `canMessage = true`. Ответить: «Готово, ответ по заявке №12 придёт сюда» |
| `/start from_app` | Ответ для оффера Mini App. **Текст промокода даёт владелец**, а до тех пор — обычное приветствие (открытый вопрос в `brief.md`, раздел 11) |
| Нажатие кнопки статуса (`callback_query`) от владельца | Сменить статус, обновить текст уведомления |
| Нажатие кнопки от кого-то другого | Отклонить |
| Ответ владельца (reply) на уведомление или пересланное сообщение | Найти заявку через `tg-msg/…` и отправить текст клиенту. Если нельзя — сообщить владельцу, почему |
| Сообщение клиента с открытой заявкой | Записать в `messages`, переслать владельцу с пометкой «по заявке №12» |
| Прочие сообщения | Короткая подсказка: команды и кнопка приложения |

Если Telegram отвечает 403 (клиент заблокировал бота), ставится `canMessage = false`, и владелец получает об этом сообщение.

### 5.4. Предоплата

1. Владелец открывает заявку → «Предоплата» → вводит сумму и описание и выбирает «Отправить клиенту».
2. Клиент получает от бота сообщение с кнопкой «Оплатить 12 500 ₽». Если бот не может писать клиенту, владелец копирует ссылку и отправляет её сам.
3. `GET /api/pay/<token>` создаёт платёж в ЮKassa:
   - `amount` из заявки;
   - `capture: true`;
   - `metadata.lead_id`;
   - `Idempotence-Key` = `token` + номер попытки;
   - `return_url` = `${SITE_URL}/?pay=<token>`.
   Затем клиент перенаправляется на страницу ЮKassa.
4. Вернувшись на сайт, клиент видит статус из `/api/pay/<token>/status`. Как и сейчас, **возврат на сайт не считается оплатой**.
5. `yookassa-webhook` получает платёж через API ЮKassa, сверяет `lead_id`, `paymentId`, сумму, `RUB` и `test: true`, ставит `succeeded` или `canceled` и пишет владельцу «💰 Заявка №12 оплачена: 12 500 ₽». Уже оплаченную запись ничто не перезаписывает.
6. Нынешние `create-payment.mjs`, `payment-status.mjs`, форма оплаты на сайте и переменные `YOOKASSA_AMOUNT_KOPEKS` / `YOOKASSA_ITEM_NAME` удаляются. Store `yookassa-orders` больше не используется.

### 5.5. Контент

- Сайт и Mini App при загрузке запрашивают `/api/content` и строят карточки из ответа. Если запрос не удался (офлайн, локальный файл), используются встроенные `site.services` / `site.portfolio` и `APP_DATA`. Пока данные загружаются, разметка не прыгает: сразу рисуются встроенные данные, затем молча заменяются.
- В админке: список карточек с полями, «Скрыть/Показать», перестановка стрелками вверх и вниз, загрузка картинки, кнопка «Сохранить». При конфликте версий появляется сообщение «Изменено в другом окне — обновите».
- Тексты из админки всегда вставляются через `textContent`, никогда через `innerHTML`.

## 7. Безопасность и надёжность

- **initData** проверяется по подписи и сроку на каждом запросе к `/api/admin/*` и при создании заявки из Mini App. `initDataUnsafe` на сервере не используется.
- **Webhook Telegram** принимается только с секретом `TELEGRAM_WEBHOOK_SECRET` (его передаёт `setWebhook` в `scripts/setup-telegram-bot.mjs`).
- **Webhook ЮKassa:** как сейчас, данным из тела не доверяем, берём только `object.id` и запрашиваем платёж у API.
- **Спам:** ловушка, лимит 5 заявок в час с одного адреса (хэш IP с солью), проверка Origin для сайта, ограничения длины всех полей. Если пойдёт поток спама, следующий шаг — Яндекс SmartCaptcha; сейчас её нет.
- **Экранирование:** в Telegram-сообщениях `parse_mode: "HTML"` и экранирование `& < >` во всех полях клиента; на страницах — только `textContent`.
- **Логи:** без имён, контактов, текстов заявок и токенов, только номер заявки и коды ошибок (как сейчас в `yookassa.mjs`).
- **Ссылки-токены** (`linkToken`, `payment.token`) создаются через `crypto.randomBytes`, их нельзя подобрать.
- **Таймауты** всех внешних вызовов — 10 с, как в `yookassa.mjs`.
- **Тесты** (`node:test`, без сети): проверка initData (верная подпись, чужая, просроченная, не владелец); валидация заявки и контента; лимит; пересчёт сумм; сценарии webhook ЮKassa и бота на хранилище в памяти. Для этого `store.mjs` принимает драйвер: в тестах — `memory`, в работе — `supabase`; драйвер Supabase проверяется на подделке его REST API.

## 8. Персональные данные — что нужно до приёма реальных заявок

Заявка содержит имя и контакты, то есть персональные данные. Бриф (раздел 4) уже отмечает это для формы. Владелец выбрал Supabase (регион США) и Netlify — оба хранят и обрабатывают данные за рубежом. Закон требует первично записывать данные граждан России в базы на территории России, поэтому **риск остаётся** до переезда хранилища.

Что делается в коде:
- Работа с хранилищем собрана в `server/lib/store.mjs`, для российского VPS уже есть драйвер `file`. Переезд — это смена `STORAGE_DRIVER` и перенос данных скриптом, код заявок не меняется.
- Хранятся только нужные поля, без IP. Есть удаление по просьбе клиента. Заявки со статусом «Готово» автоматически удаляются через **12 месяцев** после `doneAt` (`purge.mjs`; срок можно поменять в `RETENTION_DAYS`).
- Обязательная галочка согласия. Время согласия и версия политики сохраняются в заявке.

Что делает владелец (вне кода):
- текст политики обработки персональных данных (страница `privacy.html` готовится в этапе 2, текст — от владельца или юриста);
- уведомление Роскомнадзора об обработке персональных данных;
- решение о переезде хранилища в Россию до потока реальных клиентов.

Уведомления в Telegram тоже содержат данные клиента, и Telegram хранит их у себя. Это нужно учесть в политике.

## 10. Этапы разработки

Каждый этап — отдельные коммиты по-русски, без push. После каждого этапа: `npm test`, ручная проверка по `TESTING.md` (раздел дополняется на каждом этапе), отметка в этом файле. Публикация — только по слову владельца «публикуй». Каждый push тратит 15 кредитов Netlify, поэтому этапы лучше выкладывать пачкой.
